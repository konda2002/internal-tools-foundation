# Adding a tool

Each tool is a vertical slice: a migration, seed data, API routes, a page,
a nav entry and tests. Nothing in `lib/` or `components/` should need to
change for an ordinary tool; if it does, call it out in the PR.

Below, `<tool>` is the kebab-case name from the spec (e.g. `refunds`), and
`<Model>` is its Prisma model (e.g. `Refund`).

## Folder layout

```
prisma/
  schema.prisma                       + model <Model> { ... @@map("<tool>") }
  migrations/<timestamp>_<tool>/      generated by `npm run db:migrate -- --name <tool>`
  seed.ts                             + a few <Model> rows (idempotent upserts)
app/
  api/<tool>/
    route.ts                          GET list (copy the shape of app/api/audit/route.ts)
    [id]/<action>/route.ts            one POST per state change, copied from app/api/_template/route.ts
  (tools)/<tool>/
    page.tsx                          server component: header + <ToolQueue />
    <Tool>Queue.tsx                   "use client": fetches /api/<tool>, QueueTable + DetailPanel + ActionButtons
lib/nav.ts                            + { href: "/<tool>", label: "...", roles: [...] }
tests/<tool>.test.ts                  one test per rule in the spec, plus a 403 test
docs/tools/<tool>.md                  the spec this was built from (already exists)
```

## Checklist

1. **Read the spec** in `docs/tools/<tool>.md`. List every business rule; each
   one becomes a test.
2. **Schema + migration.** Add the model to `prisma/schema.prisma`. SQLite has
   no enums or JSON columns in Prisma, so use `String` with a comment listing
   the allowed values and a `z.enum` in the route. Run
   `npm run db:migrate -- --name <tool>` and commit the generated folder under
   `prisma/migrations/`. Never edit an already-committed migration.
3. **Seed.** Extend `prisma/seed.ts` with a handful of realistic rows using
   fixed ids (so tests and docs can refer to them). Keep it idempotent
   (`upsert`). Do not put seed data in migrations.
4. **API routes under `app/api/<tool>/`.**
   - Reads: copy `app/api/audit/route.ts`. `requireRole` first, then query,
     then `json(200, ...)`.
   - Writes: copy `app/api/_template/route.ts`. It is a `defineWriteRoute({...})`
     call (`lib/write-route.ts`) with one field per step:
     `role` → `body` (zod, 400) → `load` (null → 404) → `check` (throw 403/409)
     → `mutate` (inside `prisma.$transaction`) → `respond`. The helper writes
     the audit row for you in the same transaction, with actor role, request
     id and `body.reason`. Do **not** hand-roll a write route; if the helper
     can't express a case, extend it and say so in the PR.
   - If the spec requires a justification, make `reason` required in the zod
     schema (`z.string().min(3)`) and collect it with `ConfirmDialog`.
   - **All business rules live in the API.** If the spec says "only OPS_LEAD
     may approve over $500", that is a check in the route, not just a disabled
     button.
   - Use the helpers in `lib/api.ts` (`errors.forbidden()`, `errors.conflict()`,
     `errors.notFound()`), never hand-rolled `NextResponse.json({ message })`.
   - Audit `action` is `"<tool>.<verb>"` (`refund.approve`), `entityType` is
     the model name in lower case, `before`/`after` are the full row.
5. **Page under `app/(tools)/<tool>/`.** Build it from the kit only:
   - `AppShell` is already applied by `app/(tools)/layout.tsx`.
   - `QueueTable` for the list (`searchable`, `defaultSort`, `pageSize` are
     built in), `DetailPanel` for the selected row, `ActionButton` for each
     action with a `disabledReason` that mirrors the API's rule (e.g.
     `"Only OPS_LEAD can approve"`). The button is a hint; the API decides.
   - `ConfirmDialog` before every state change; pass `requireReason` when the
     spec wants a justification and send it as `reason` in the POST body.
   - `TextField` / `SelectField` for any inputs (create/edit forms, filters).
   - Fetch from `/api/<tool>` on the client and render the API's error
     message when it returns 403 — never pre-check roles in the page.
6. **Nav entry** in `lib/nav.ts` with the roles that may use the tool.
7. **Tests in `tests/<tool>.test.ts`.** Import the route handlers directly and
   call them with a `Request` (see `tests/template.test.ts` and
   `tests/helpers.ts` for `cookieFor(email)` / `jsonRequest(...)`). Required:
   - one **403** test (wrong role),
   - 400 (bad body), 404 (missing id),
   - one test per business rule in the spec (403 or 409),
   - the success path, asserting the audit row exists with the right
     `action`, `before` and `after`.
   The test database is rebuilt from migrations + seed on every `npm test`.
8. **Docs.** Add the tool to the README table of pages/logins if it introduces
   new roles or demo data worth knowing about.
9. **Verify** `npm run setup && npm run dev` works from a clean checkout,
   `npm test`, `npm run typecheck`, `npm run lint`.
10. **Open one PR** with screenshots of the new page in each relevant state.
    If you changed anything outside the tool's own folders (foundation files),
    say so explicitly in the description.
